## 一、先看第一性原理：这个技能到底在防什么

剥离「插件、Cordis、upgrade-guide」这些名词，一件事的内核是：

> **A 方（宿主）单方面改了自己的接口，B 方（第三方插件）在没有同步信息、没有同步节奏、也没有同步权限的情况下，还必须继续工作。**

由此推出四个不可省略的动作，且顺序固定：

1. **知道变了什么** —— 需要上游的变更声明（不是人写的卡片）
2. **知道自己的代码有没有踩** —— 需要把声明变成可匹配的锚点，再扫自己的代码
3. **验证结论** —— 静态匹配不足以证明能跑
4. **在变之前先不踩** —— 写新代码时按常设要求写

再往下一层问：**哪一类事实是「会变的」，哪一类是「不变但会被违反的」？**

| 事实类别 | 性质 | 上游正家 | 本轮前的覆盖 |
| --- | --- | --- | --- |
| 版本位置与目标 | 会变，每隔 1.7~2.8 天一个预发布 | npm `dist-tags` | 有（`guide-sync`） |
| 破坏性变更与官方修法 | 随版本线性累积 | `docs/upgrade-guide/` | 有（`code-scan`） |
| **常设硬要求（不随版本变）** | **不变，但插件随时可能违反** | **`docs/defensive-patterns/`** | **无** |
| **落盘格式变更（旧数据还能不能读）** | **随版本变，且是单向门** | **`docs/persistence-changes/`** | **无** |

这是本轮最重要的一条发现：**技能原先只覆盖了「前半张」，而前后两半互不覆盖。**

- 一份插件可以通过全部升级指南扫描，仍然违反常设要求（例如模块顶层 `await`、导出面多了一个默认导出、注册可变的模块级单例）。
- 反过来，常设要求永远不会出现在任何一版的 upgrade-guide 里——它不是「变更」，是「一直如此」。

所以「命中 0 处」原先有个未被言明的含义：**只代表没踩版本变更，不代表合契约**。这一点原先在 `SKILL.md` 里靠一句「零命中不代表没问题」暗示，但没有可执行的第二来源，暗示落不了地。

## 二、MECE 拆解：四条车道的覆盖与重叠

### 2.1 现状矩阵（按「问题生命周期」而非工具划分）

| 阶段 | 谁在管 | 产物 |
| --- | --- | --- |
| 写代码 | build（scaffold / write-gate） | 出生证 |
| 装完不生效 | diagnose（log-doctor / env-doctor / env-heal） | 根因 + 动作 |
| 版本升级踩变更 | adapt（guide-sync / code-scan / seams / plugin-audit） | P0/P1 命中 + 官方修法 |
| 深度架构审查 | review（plugin-audit --compact / 子 Agent 委派） | 四级严重度报告 |
| 批量 | fleet-sweep（跨车道） | 矩阵看板 |

### 2.2 重叠：三处真实冗余（按奥卡姆判断留不留）

| 重叠 | 判断 | 处置 |
| --- | --- | --- |
| `run.mjs` 与 `write-gate.mjs` 都在编排「冒烟 + 体检 + 扫描」 | 门槛位置不同（日常编排 vs 交付门），编排成本可忽略 | **保留**，但把「两者判据不同」写进 SKILL.md |
| adapt 第六步与 review 第一步都调 `plugin-audit` | review 用 `--compact` 是 adapt 的严格子集 | **保留**（同一脚本两种读法，不是两份实现） |
| 主入口与 `sub-skills/adapt` 都写了扫描窗口说明 | 真冗余：同一条「不要盲目取 latest」在 4 处出现 | **只保留主入口结论 + adapt 的判据**，其余放 references |

### 2.3 缺口：两处 MECE 意义上的空集

1. **常设契约无来源**（第一节已述）——adapt 与 review 都在讲「防御性」，但两边的判据都是本技能自写的启发式，没有接上游原文。
2. **持久化兼容无归属**——上游有 `docs/persistence-changes/` 二十余份变更（含 session-format-v4、unknown-child-catalog、working-directory-attribution），插件升级后「旧数据读不出来」这一类故障**四条车道都不管**：adapt 只管代码符号，diagnose 只管启动期，review 只看静态代码。

### 2.4 边界外的空白（明示不覆盖，避免假装 MECE）

- 生态分发面（npm 包名抢占、marketplace 上架规则）
- 插件之间的相互依赖冲突（上游未定义插件间依赖语义）
- 权限模型与沙箱策略
- 运行时性能剖析（只做静态提示，不做度量）

## 三、同类与上游项目的真实问题（带出处）

三类证据分开列，不混着说。

### 3.1 上游一手文档与源码（最硬）

| 发现 | 出处 |
| --- | --- |
| 常设硬要求共五篇，覆盖包面、客户端组件、会话、远程 API、通用时序/状态 | `docs/defensive-patterns/README.zh.md` |
| **「新增 active/current 单例一律禁止」**、**「共享状态只有一个所有者」**（模块级缓存、全局 WeakMap、`Symbol.for`、`globalThis.__X__` 全属违反） | `docs/defensive-patterns/general.zh.md` |
| **「包模块不在模块顶层 await」**（有专门门禁脚本 `verify-no-top-level-await.ts`） | `docs/defensive-patterns/package-surface.zh.md` |
| **「新增 resolve 钩子直接禁止」**（确定性禁止，不是「尽量不」） | 同上 |
| 插件入口只允许两种形态且不得混用：函数插件具名导出 `name/inject/Config/apply`，服务插件默认导出服务类；**在四件套旁加默认导出会让 Loader 丢掉整个命名空间** | `docs/defensive-patterns/package-surface.zh.md`，并已立为事故复盘 `docs/postmortem/0001-acp-default-export-drops-inject.md` |
| **「用 unlink 删除链接形态的路径」**：`rmSync(link, { recursive: true })` 在 POSIX 会穿过链接删目标，Windows 对 junction 抛 `ERR_FS_EISDIR` | `docs/defensive-patterns/general.zh.md` |
| **「绝不将环境变量或可预测路径暴露给不可信输出」**：启动命令须用清理过的环境变量，移除匹配 `*KEY*`/`*SECRET*`/`*TOKEN*`/`*PASSWORD*` 的项 | 同上 |
| 落盘格式变更有独立目录与目录，`docs/persistence-changes/` 逐份记录；宿主另有 `docs/persistence-catalog.json` | 仓库目录 |

**关键发现（自指）**：上游在 `packages/boot/plugin-manager/tests/git-environment.ts` 里**明文记录**了一个环境残缺现象，原文：

> Git exports its indexed command-line configuration (`GIT_CONFIG_COUNT` with `GIT_CONFIG_KEY_n` / `GIT_CONFIG_VALUE_n`, or the older `GIT_CONFIG_PARAMETERS`) to `git -c` calls and to hook children. The shared subprocess scrub removes credential-shaped names, so a child that inherits the counter without its key fails before it reads any configuration file (`error: missing config key GIT_CONFIG_KEY_0`).

也就是说：**宿主的子进程凭证擦除按变量名过滤，而 `KEY` 三个字母同时是「git 配置通道名」与「密钥字段名」——擦除必然砸中 git 配置组，把环境变成残缺态。** 上游自己的测试用 `isolateGitCommandLineConfig()` 绕开，上游自己的 git 调用点显式写 `GIT_CONFIG_COUNT: '0'`（`packages/deliverables/workspace-changes/src/git.ts`）。详见 §4.1。

### 3.2 本机实测（可复现）

| 发现 | 命令与结果 |

### 3.3 同类项目的真实事故（带 URL，可按需再核）

**插件宿主框架**

- `engines.vscode` 是**安装期硬门**，不匹配直接拒绝安装，报错原文 `Unable to install extension ... as it is not compatible with the IDE`。[vscode#298420](https://github.com/microsoft/vscode/issues/298420)、[publishing-extension](https://github.com/microsoft/vscode-docs/blob/main/api/working-with-extensions/publishing-extension.md)
- **API 提案（proposed API）不兼容会让扩展在所有可下载宿主上都激活失败**，宿主与插件谁先发布都会造成一侧无解。[vscode#300399](https://github.com/microsoft/vscode/issues/300399)、[#329735](https://github.com/microsoft/vscode/issues/329735)
- `vscode` 模块漏进 `dependencies` 是打包层静默雷：该模块只由扩展宿主运行时注入，npm 上的同名包是历史类型桩。[vscode-docs#3678](https://github.com/microsoft/vscode-docs/issues/3678)
- Chrome MV2→V3 破坏的是**运行模型**而非签名：后台页换 service worker（随时可被终止，全局状态无法常驻）、远程代码与 eval 被禁。[MV3 迁移](https://developer.chrome.com/docs/extensions/mv3/intro/mv3-migration)
- Figma 的坑在**类型声明与运行时不一致**：`plugin-typings` 是手写投影，编译通过 ≠ 宿主可运行。[plugin-typings#386](https://github.com/figma/plugin-typings/issues/386)
- **Obsidian 官方 lint 把「声明 vs 实际调用」做成可自动判定的硬错**：拿代码实际调用的 API 比对 `minAppVersion`，不一致即 Error 阻断重提。这是全批里最值得抄的一条。[obsidian-synapse#294](https://github.com/dustinkeeton/obsidian-synapse/issues/294)
- Obsidian 把资源释放写进条款：插件被禁用后仍在用的资源会造成宿主性能问题，释放点固定在 `onunload()`。[Anatomy of a plugin](https://github.com/obsidianmd/obsidian-developer-docs/blob/main/en/Plugins/Getting%20started/Anatomy%20of%20a%20plugin.md)

**Node / npm 插件系统**

- **npm 7 起 peer 依赖从告警升级为硬失败**，且失败模式随小版本漂移；`npm ci` 不带 `--legacy-peer-deps` 直接 ERESOLVE；范围写 `>=` 也会误判。[npm/cli#4998](https://github.com/npm/cli/issues/4998)、[#4664](https://github.com/npm/cli/issues/4664)、[#2553](https://github.com/npm/cli/issues/2553)
- **宿主与插件共享模块的版本协商有五种已记录失效形态，全部表现为「静默绑错版本」**：`strictVersion` 对 singleton 不生效、`version-first` 下 singleton 解析到宿主自身版本、版本号相等时 `hostInit` 仍重新实体化 singleton 产生第二个实例（`useContext` 变 null）、非 singleton 只在版本完全相等时复用、`singleton: false` 也不保证多版本并存。**这五条全部是「构建通过、浏览器里才炸」。** [module-federation/vite#1452](https://github.com/module-federation/vite/issues/1452)、[#1247](https://github.com/module-federation/vite/issues/1247)、[#1331](https://github.com/module-federation/vite/issues/1331)、[#1503](https://github.com/module-federation/vite/issues/1503)、[#755](https://github.com/module-federation/vite/issues/755)
- Yarn PnP 下依赖里 `require.cache` / `require.extensions` 未定义，打断单例检测与热挂载。[nodejs/node#64709](https://github.com/nodejs/node/issues/64709)

**Agent 宿主与协议层**

- MCP 协议协商失败的一个真实形态：客户端把版本协商结果带成**区间**（`2025-11-25, 2025-03-26`），服务端 `validateProtocolVersion()` 拒收，connect 阶段硬失败。[typescript-sdk#2969](https://github.com/modelcontextprotocol/typescript-sdk/issues/2969)
- 官方 spec 在 2025-06-18 **移除 JSON-RPC batching**、把 `MCP-Protocol-Version` 头改为强制、把 lifecycle 的 SHOULD 改 MUST。[changelog](https://modelcontextprotocol.io/specification/2025-06-18/changelog)
- **同一会话重复 initialize 会覆盖已协商的 client_params**（静默重写，不报错）。[python-sdk#2605](https://github.com/modelcontextprotocol/python-sdk/issues/2605)
- **插件写死的宿主变量未被目标宿主插值**：Codex 镜像 Claude Code 市场，`${CLAUDE_PLUGIN_ROOT}` 被当字面量透传，子进程报 ENOENT，日志落在 `handshaking with MCP server failed`。[codex#19582](https://github.com/openai/codex/issues/19582)
- **工具名长度与字符集直接决定工具能否被用上**：超 63 字符截断后碰撞、注册表静默掉一个工具。[gemini-cli#28970](https://github.com/google-gemini/gemini-cli/issues/28970)
- **插件/工具重复注册默认为「静默覆盖」**（last-write-wins，无警告）。[agentRoadmap#4](https://github.com/agentroadmap/agentRoadmap/issues/4)
- **一次插件生命周期重载会把活会话里的工具句柄变陈旧**，直到整进程重启才自愈；「失败并已声明回滚」的热重载更会让无关插件持续抛错。[openclaw#156883](https://github.com/openclaw/openclaw/issues/156883)
- **会话持久化格式变更导致旧 transcript 不可读**：某项目 4 天内 9 个会话的 `.jsonl` 静默丢失，`/resume` 不可恢复，且官方与用户都无法定位从哪个版本开始停写。[claude-code#102106](https://github.com/anthropics/claude-code/issues/102106)
- **指令文件静默截断**：Codex 对 `AGENTS.md` 按 32 KB 截断，超出部分的规则被丢弃且各处无警告。[codex#13386](https://github.com/openai/codex/issues/13386)
- **MCP 工具定义注入本身就吃掉上下文大头**：官方给出的五服务实例合计 58 工具 ≈ 55K token，尚未开始对话；内部见过 134K。[Anthropic: advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)
- **残缺 git 配置组在同类项目里也被踩过**：Renovate 子模块操作报同一句错（用户环境里正有 `GIT_CONFIG_COUNT: '2'`）[renovate#40575](https://github.com/renovatebot/renovate/discussions/40575)；GitHub Desktop 提交时报 `GIT_CONFIG_VALUE_0` 相关错误，38 条评论、三个月才在 beta 修复 [desktop#18945](https://github.com/desktop/desktop/issues/18945)；libgit2 至今不支持 `GIT_CONFIG_PARAMETERS`，同一份 `-c` 配置在命令行 git 生效、在嵌入库静默不生效 [libgit2#3854](https://github.com/libgit2/libgit2/issues/3854)

**通行解法（三条，可直接抄）**

1. **原子化**：要留就三件套一起留，要么整组丢，绝不按名字逐条过滤。
2. **白名单**：pre-commit 的 `no_git_env()` 剥掉所有 `GIT_*`，但显式豁免 `GIT_CONFIG_KEY_` / `GIT_CONFIG_VALUE_` / `GIT_CONFIG_COUNT`（注释写「Too many bugs dealing with environment variables and GIT」）。[pre_commit/git.py](https://raw.githubusercontent.com/pre-commit/pre-commit/main/pre_commit/git.py)
3. **客户端默认禁用、要求显式开启**：simple-git 3.36.0 起不给 `allowUnsafeConfigEnvCount` 直接拒跑。

**一个必须记进清单的边界**：`GIT_CONFIG_VALUE_n` 是**危险而残留**的那一半——它可以携带 `-c http.extraHeader=...` 之类的凭据，而按名字擦除恰好留下它、删掉非机密的键名。也就是说残缺态不只是「坏」，还是**安全不对称**的。

## 四、本轮改了什么（每条只答「以前不行、现在能行」）

### 4.1 宿主会话内所有 git 调用会静默失败 → 现在能跑（P0，本工具自坏）

**以前**：`env-doctor` 的 `gitCheckoutInfo` 静默吃异常返回 `null`（幽灵宿主判定退化成「磁盘时间来源不明」，用户看不出是失败）；`guide-sync` 的 fetch/clone/reset 全挂；`release-check` 的 tag 与工作区检查全挂；自检在宿主会话内 2 项假失败。四处症状，同一个根因，且**全都表现为「没结果」而不是「报错」**——最难查的一类。

**现在**：新增 `scripts/lib/proc-env.mjs`，在工具自己的边界上判定并净化。判据不是猜的：git 只在「声明了 `GIT_CONFIG_COUNT` 但任一 `KEY_i` 缺失」时报那句话；**组齐全时一个字节都不动**（合法用法不能被误伤），组残缺时摘掉整组并把 `GIT_CONFIG_COUNT` 落成 `'0'` 显式表达「零组命令行配置」，且不碰 `GIT_CONFIG_GLOBAL` / `SYSTEM` / `NOSYSTEM` 这三个单键。七个调用点（guide-sync 8 处 git、env-doctor、sync-skill、runlog、release-check）+ 自检自身的子进程环境全部收口。

**为什么不在全局改 `process.env`**：本工具是别人会话里的一个进程，替用户改环境是越界。净化放在「谁起子进程谁负责」这一层，退出即还原。

新增 8 项断言，其中一条是**真跑 git** 的回归：把残缺组显式交给 git，不净化就会复现 `missing config key`，净化后 `init/add/commit/status` 全通。

### 4.2 删路径会穿过软链删目标 → 现在按链接语义删（P1，数据丢失）

**以前**：`guide-sync` 对受管缓存目录三处 `rmSync(dir, { recursive: true, force: true })`；`quick-smoke` 对临时软链兜底目录同理。若用户把 `~/.cache/dsh-plugin-fast-adapt` 软链到别处（省盘空间的常见做法），递归删会**跟着链接删掉目标内容**——纯数据丢失，且发生在「清缓存」这种心理上安全的动作里。

**现在**：`removeDirSafely()` 先 `lstat` 判定，链接与文件走 `unlinkSync`（只删链接本身、对真实目录会拒绝），真实目录才递归删；返回「实际发生了什么」。这条的判据直接来自上游常设规则「用 unlink 删除链接形态的路径」，不是自创。

### 4.3 只扫升级指南 → 现在四类来源分开管（覆盖缺口）

`SKILL.md` 从「**权威来源只有两处**」改为**四类来源表**（npm dist-tags / upgrade-guide / defensive-patterns / persistence-changes），并把「前两类管时间轴上的破坏性变更，后两类管不随版本变的常设契约，二者不可互替」写成结论句——因为「只扫升级指南等于只查了一半」这件事原先没有一句话说清。

## 六、未做的事与待确认项

1. **持久化兼容只登记了来源，没做检查器**。需要一份真实故障样本（插件升级后旧数据读不出）才值得动手。
2. **`defensive-patterns` 的机器可读解析没做**。目前只在文档层指路；若要真正扫描「模块顶层 await」「多出第五个导出」「模块级可变单例」这类常设违规，需要一个锚点抽取器——上游有对应门禁脚本（`verify-no-top-level-await.ts`）可作锚点来源。
3. **`GIT_CONFIG_VALUE_n` 的凭据残留是安全问题，不是本工具的问题域**，已在报告登记，建议在宿主侧或专门的密钥扫描插件里处理。
4. **本机 `~/.npm_cache` 属主被 root 污染**，`npm pack` / `npm view` 全 EPERM。这是环境问题，会让 `release-check` 的 pack 项 FAIL、npm 项 unknown；修法是 `sudo chown -R 501:20 ~/.npm_cache`，**需要用户自己执行**。
5. **`run.mjs` 是否要把「常设规则来源」纳入扫描阶段未定**：纳入就要有锚点抽取器（见第 2 点），不纳入则 review 车道手工核对。倾向前者，但先等第 2 点的判据成熟。
